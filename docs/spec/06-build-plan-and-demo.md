# Build Plan, Verification, and Demo

## Delivery sequence

### Phase 0 — Inspect repository
Inspect package files, framework, routes, scripts, tests, and deployment. Preserve working code. Confirm constraints and deployment target.

### Phase 1 — App shell
Build responsive navigation, landing page, guest entry, design tokens, and meaningful loading/error/empty states.

### Phase 2 — Scenario vertical slice
Define typed content, author one original scenario pack, implement evaluator, hints, feedback, rationales, and fresh retry. Add unit tests.

### Phase 3 — Progress and revision
Record attempts, derive objective evidence, implement scheduler and review UI, persist locally, test refresh and invalid storage.

### Phase 4 — Architecture Canvas
Select a React-compatible accessible diagram library. Build small palette, nodes/edges, inspector, structured list alternative, guided challenge, and 2–3 deterministic simulation rules. Document assumptions.

### Phase 5 — Track/auth proof
Add registry and a small second neutral/AWS sample pack. Integrate real managed auth only if properly configured; otherwise label auth UI as demo.

### Phase 6 — QA and documentation
Run available lint/typecheck/tests/build; check keyboard/mobile paths; verify no copied exam items, logos, secrets, or cloud provisioning. Update README and known limitations. Deploy and smoke-test.

## Prioritization
A feature enters MVP only if it strengthens the core learning loop or proves a key differentiator. Defer breadth that compromises polish and reliability.

## 3–4 minute demo
1. State the proposition: learn cloud through decisions, not copied exam questions.
2. Enter as guest and select Azure track.
3. Make a plausible wrong choice in a scenario.
4. Show consequence, explanation, misconception, and objective.
5. Retry with a fresh transfer challenge.
6. Add concept to revision and show progress update.
7. Build a small conceptual diagram and run a failure/security simulation.
8. Show assumptions and learning follow-up.
9. Explain evidence-based mastery is not a pass guarantee.
10. Show that another content pack uses the same engine.

## Release checklist
- [ ] Setup commands in README are verified against actual scripts.
- [ ] No dead primary buttons or fake integrations.
- [ ] Guest flow works.
- [ ] Auth state is honestly represented.
- [ ] Responsive and keyboard flows work.
- [ ] Simulation is deterministic and scoped.
- [ ] Content maps to objectives and sources.
- [ ] Persistence/privacy limitations are documented.
- [ ] No real cloud credentials/resources used.
- [ ] README distinguishes implemented, partial, planned, and known issues.
